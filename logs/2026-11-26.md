## 1. The server shut down on its own

**Symptom:** the server was off in the morning. It had been up since the SSD swap the day before.

**What the logs showed:**
- The journal stopped mid-sentence at **08:42:34**, in the middle of normal DNS traffic. There was no shutdown sequence, and the next boot found the journal "uncleanly shut down."
- `last` recorded my SSH session as ending in **crash**.
- No out-of-memory kills, kernel panic, lockup warnings, overheating, or disk errors. The new SSD logged nothing.
- **Not a power cut:** the laptop battery was at 99% and on AC.

**Best lead:** between 08:05 and 08:10 swap filled to **99.9%** and I/O wait jumped to 21% (from `sar`). That lines up with the nightly Backrest backup at 08:00. Yesterday's swappiness change helped but didn't remove the pressure. Nextcloud also updated itself at 07:41, but that finished long before the spike.

**Verdict:** a hard freeze, with no definite cause. If it happens again, the next step is a RAM test (memtest86+) and a look at memory use during the backup.

**Lesson:** when the journal just stops, with no shutdown and no error, think freeze or power loss, not software. And check what's scheduled near that time. I first blamed the Nextcloud update; the backup timing fit better.

## 3. "I couldn't reach the Pi either"

While the server was down, I couldn't SSH into the Pi or open the Pi-hole page. It looked like the Pi had lost its connection too. It hadn't: the Pi's logs showed it resolving DNS normally the whole time. Three separate things were going on.

1. **Tailscale routed home traffic through the server.** The server was the only Tailscale *subnet router* for the home network. Windows Tailscale sends home-network traffic through the subnet router even when the PC is at home on the same network, so with the server off, the Pi's home address was unreachable from my desktop.
   **Fix:** the Pi now advertises the same route. I turned on IP forwarding (`/etc/sysctl.d/99-tailscale.conf`), ran `tailscale set --advertise-routes=…`, and approved the route in the admin console. Tailscale keeps one router active and switches to the other when it drops.
2. **The Pi-hole web page isn't on port 80.** It's on a custom port, so opening the bare IP shows nothing.
3. **SSH refused the Pi's host key.** I'd reflashed the Pi 3–4 weeks ago, and the server still had the old keys. I removed them with `ssh-keygen -R`, made an SSH key on the server, and copied it to the Pi.

**False alarm:** at one point the Pi-hole answered `google.com` with `192.179.x.x` addresses, which looked like DNS hijacking. An RDAP lookup showed that range belongs to Google. Check before panicking.

**Still to decide:** the server is the only Tailscale *exit node*. If a device sends all its traffic through it, that device loses internet when the server is down. The Pi could be a backup exit node too.

## 5. Getting the server back on after a power cut

The server is a laptop. In a power cut the battery keeps it running, but once the battery dies it stays off. This ASUS has no BIOS "power on with AC" setting.

### Wake-on-LAN: didn't work

The plan was for the Pi to send a Wake-on-LAN packet when it booted after the power returned. I enabled it on the ethernet adapter (`wakeonlan: true` in netplan) and wrote a small script for the Pi.

**Test:** I powered the server off and sent six magic packets. The hub's link light stayed on, but the laptop didn't wake.

**Why:** `/proc/acpi/wakeup` lists the USB controller as able to wake the laptop only from **S3** (sleep), not **S5** (off). The ethernet adapter sits on a USB-C hub, so the packets arrive but the firmware ignores them. No software setting changes that. I removed the Pi script.

### The real-time clock alarm: works

The kernel said `rtc_cmos: RTC can wake from S4`, which suggested the clock alarm might wake it from off too. I tested it:
```bash
sudo rtcwake -m off -s 180
```
The server shut down at 09:42 and **powered itself on at 09:45:40**, with no button press.

### power-guard

I built a small cycle on that alarm ([`scripts/power-guard`](../scripts/power-guard)):

- **Every minute** (a systemd timer): if on battery at 20% or less, set a 30-minute alarm and power off cleanly.
- **At boot** (a service that runs before Docker and the VMs start): if still on battery at 25% or less, set another alarm and power off again within seconds.
- On AC power it always boots normally. If it can't read the battery, it does nothing.

Worst case, the server is back within about 30 minutes of the power returning. Switched off, it draws almost nothing, so 20% of the battery covers days of checks. I also changed UPower's critical-battery action from `HybridSleep` to `PowerOff` as a backstop.

**Tested:** the clock-alarm wake (for real) and every branch of the script (dry run).
**Not yet tested:** a real run with the charger unplugged.

### The Pi

The Pi 4 is in an **Argon ONE M.2** case, which by default waits for its power button after power returns. A jumper on the case board switches it to **"Always On"**. I moved it, and the Pi now boots as soon as it's plugged in.

## 6. Recovering from a hung network connection

I wanted the server and the Pi to restart themselves if they lost the network. A plain "reboot when the internet is down" causes reboot loops during an ISP outage, which a reboot can't fix. So [`scripts/netwatch`](../scripts/netwatch) checks once a minute and separates the cases:

| What it sees | What it does |
|---|---|
| Can't reach the router (a problem on this machine) | Resets the network adapter after 3 min; reboots after 10 min, at most 3 times in 24 hours |
| Router fine, internet down (ISP or modem) | Logs it, nothing else |
| On battery (power cut, so the router is down too) | Nothing; power-guard handles it |

On the server it resets only the USB ethernet adapter, not the bridge, because the bridge also carries the Home Assistant VM. I tested the reset for real: about 3 seconds of downtime, then the adapter rejoined the bridge and the router, internet and VM all answered. The reboot step is only tested in a dry run.

The Pi runs the same script on its own ethernet port. The logs show no past link drops on either machine, so this is a precaution, not a fix for something already happening.

## What a power cut looks like now

1. The power goes out. The Pi turns off; the server keeps running on battery.
2. The battery reaches 20%. The server sets a 30-minute alarm and shuts down.
3. Power returns. The Pi boots at once. Tailscale moves the home route to the Pi.
4. The server's next alarm fires. It sees AC power and boots normally.
5. Both machines watch their network connection from then on.
