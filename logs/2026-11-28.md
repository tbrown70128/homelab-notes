# Homelab log: November 28, 2026

The server was off when I checked on it, and it hadn't come back by itself. The cause turned out to be heat: a stuck Nextcloud job kept one CPU core at 100% for 13 hours until the laptop hit its 100°C thermal cutoff. I fixed the job, then spent the rest of the day making sure I find out about problems like this and that the server recovers from them on its own.

Times are UTC; Eastern is 5 hours behind.

## 1. Why the server was off

**Symptom:** the server was off in the morning and had to be switched on by hand at 06:12.

**What the logs showed:**
- The journal stopped mid-stream at **23:02:08 on Nov 27**, in the middle of normal DNS traffic, with no shutdown sequence. On the next boot the journal and two filesystems were flagged as not cleanly unmounted.
- **Not a power cut:** the charger was connected (battery voltage steady) and the Pi, on the same power, stayed up.
- **Heat:** Netdata's sensor history showed the CPU going from about **60°C to 95°C** around 09:25 on Nov 27 and staying there for 13 hours, with the fan pinned at 4,900 rpm and peaks of **98°C**. The cutoff is 100°C. Load average was only about 2.5, so this wasn't the server being busy.

**Finding the process:** Netdata's per-app CPU charts showed one PHP process inside the Nextcloud container jumping to about **99% of one core at 09:26**. Nextcloud's job table showed the **Announcements crawler** (`OCA\NextcloudAnnouncements\Cron\Crawler`) started at 09:25:04 and never finished; it was still marked as running. Running that one job by hand with a 60-second time limit sent it straight to 95% CPU until the limit killed it, so it's stuck in a loop (Announcements 7.0.0 on Nextcloud 35.0.3).

**Fix:** `occ app:disable nextcloud_announcements`. Its job is gone from the queue. It only shows Nextcloud's own news.

**Lessons:**
- When the journal just stops with no shutdown, check temperatures before blaming software. Netdata keeps the sensor history.
- Netdata's per-app and per-container CPU charts (`app.*`, `cgroup_*`) pin down a culprit to the minute.
- The laptop's cooling margin is thin: it lives closed in a vertical stand, and a single busy core was enough to reach the cutoff.

## 2. Why it didn't come back on

The power-guard from Nov 26 only sets a wake-up alarm before its own low-battery shutdown. A thermal cutoff is instant and done by the hardware, so nothing ran to set an alarm, and this laptop has no "power on when AC is connected" setting.

## 3. CPU temperature alert

[`heat-alert`](../scripts/heat-alert) runs every minute:
- **90°C for 5 minutes:** Discord alert, repeated hourly while it stays hot.
- **97°C:** alert straight away, at most every 15 minutes.
- **Below 80°C:** "back to normal".
- Each alert lists the top three CPU users with their container or VM name, so a stuck job like this one would show up as PHP in the Nextcloud container.

It uses the same Discord webhook as Backrest and Uptime Kuma.

---

## 4. Powering back on after a sudden power-off

The idea is a **rolling wake-up alarm**: [`wake-arm`](../scripts/wake-arm) pushes the real-time clock alarm 10 minutes into the future every minute. While the server runs, the alarm never goes off. If it dies suddenly, the last alarm is still set and boots it.

- **Deliberate shutdowns stay off:** a clean shutdown clears the alarm. Power-guard and the heat shutdown mark their own alarms to be kept.
- **Unexpected power-offs:** a flag file that's still there at boot means the last power-off wasn't clean. It's logged, and Discord gets an "unexpected power-off" message.
- **Restart limit:** after 3 unexpected or heat power-offs within 6 hours it stops auto-restarting and says so in Discord, so a persistent fault can't cycle it all night. `sudo wake-arm reset` turns it back on.
- **Clean heat shutdown:** two readings in a row at 98°C or more → Discord alert, 20-minute alarm, normal shutdown, instead of waiting for the hard cutoff.

**First real test failed.** I held the power button until the laptop turned off. The alarm was set in the clock chip, but it stayed off. The cause: the ACPI "wake on RTC alarm" event (`/sys/firmware/acpi/interrupts/ff_rt_clk`) is **disabled while Linux is running**. Linux only enables it during a clean shutdown, which is why the Nov 26 test, a clean `rtcwake -m off`, had worked. `wake-arm` now writes `enable` there every minute and right at boot.

**Second real test passed:** powered off with the button at 07:24:54, and it powered itself on at 07:35:04.

**Lesson:** an RTC alarm that wakes a machine from a clean shutdown doesn't prove it will after a hard power-off. Test the failure you're actually protecting against.

## 5. Hardware watchdog

The rolling alarm can't help with a freeze, because the machine never turns off. The chipset has an Intel TCO watchdog (`iTCO_wdt`):
- systemd now pings it (`RuntimeWatchdogSec=60s`, `RebootWatchdogSec=10min`), so a hang of 60 seconds resets the machine.
- **Gotcha:** Ubuntu blacklists the watchdog drivers in `/lib/modprobe.d/blacklist_linux_*.conf`, and `systemd-modules-load` honours that list. A small `itco-watchdog.service` runs `modprobe iTCO_wdt` by name at boot instead.
- After the reboots in section 4, PID 1 logged "Watchdog running with a timeout of 1min".

## 6. Hearing about it when the server is down

Every alert source (Uptime Kuma, heat-alert, wake-arm) runs on the server, so a dead server stays silent.

**The Pi watches the server:** [`server-watch`](../scripts/server-watch) runs every minute as my user on the Pi (a systemd user timer with lingering on, so no sudo):
- The server counts as up only if its SSH service answers. Ping and Uptime Kuma are also checked, just to explain the fault: ping but no SSH means frozen, no ping means off.
- After 3 failed checks in a row: "🔴 DOWN" with the likely reason, a reminder every 6 hours, and "🟢 back up after N min".

**Internet outages:** while the internet is down nothing at home can reach Discord, and Uptime Kuma simply drops alerts it can't send. `server-watch` pings three public resolvers. After 2 failed checks in a row it counts the internet as down, and when it's back it posts "🌐 Internet was down from X to Y (N min)". Anything it couldn't send in the meantime is queued and delivered after that, tagged with when it happened. Tested with a simulated outage against a fake local webhook.

**healthchecks.io (free plan)** covers the time *during* an outage:

| Check | Who checks in | An alert means |
|---|---|---|
| server | the server, every minute | the server is off, frozen, or offline |
| home internet | the Pi, every minute (only when its internet check passes) | the internet or the house power is down |

Each check has a 1-minute period and 3 minutes' grace, and alerts by email and Discord. If both checks alert, it's the internet or the power; if only the server's does, it's the server.

## 7. Uptime Kuma: Pi-hole monitor

The "Laptop Server Pi-Hole" group had a web check pointed at the Pi's Pi-hole instead of the server's, so it would stay green even if the server's Pi-hole died. I stopped Uptime Kuma briefly, backed up `kuma.db`, changed that one monitor's URL, and started it again. It came back at 200 OK.

## Still open

- **Cooling margin:** with the stuck job gone the CPU idles around 45–60°C, but one busy core was enough to reach the cutoff. Clean the fan and vents; think about the closed lid in the vertical stand.
- **Uptime Kuma during an outage:** its own alerts are still lost while the internet is down. healthchecks.io and `server-watch` cover the server and the internet, not individual services.
- **Real power-cut test** with the charger unplugged (from Nov 26) is still to do.
- **The Nov 26 freeze was a different problem:** it was also a hard stop with nothing in the logs, but Netdata shows the CPU at 59–74°C in the half hour before it (the peak was 91°C briefly at about 08:09, during the backup). The memory-pressure theory still stands. The new watchdog should now reset a freeze like that by itself.

## Mistakes
